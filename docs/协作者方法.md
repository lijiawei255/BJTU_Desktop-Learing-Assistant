## 一、初始搭建（只做一次）

### 1.1 安装 Anaconda3

前往 [anaconda.com/download](https://www.anaconda.com/download) 下载 Windows 版并安装。

> 如已安装 Anaconda3，可跳过此步。终端输入 `conda --version` 确认可用。

### 1.2 获取阿里云百炼 API Key

1. 访问 [阿里云百炼控制台](https://bailian.console.aliyun.com/)
2. 登录后进入「模型服务」→「API Key 管理」
3. 创建新的 API Key 并复制保存

> 项目使用千问系列模型（LLM + ASR + TTS），统一通过百炼 API 接入。API Key 是调用这些服务的凭证，每人需用自己的 Key。

### 1.3 克隆仓库

```bash
git clone https://github.com/lijiawei255/BJTU_Desktop-Learing-Assistant.git
cd BJTU_Desktop-Learing-Assistant
```

### 1.4 一键创建 Conda 环境

```bash
conda env create -f environment.yml
conda activate amiya
```

> `environment.yml` 定义了与主开发者完全一致的 Python 3.11 环境及所有依赖包。创建过程约 2-5 分钟。

### 1.5 配置 API Key

```bash
cp .env.example .env
```

用文本编辑器打开 `.env`，将 `sk-your-api-key-here` 替换为步骤 1.2 中获取的百炼 API Key：

```
ALIBABA_API_KEY=sk-你的真实Key
```

> `.env` 已被 `.gitignore` 排除，不会被提交到 GitHub。**请勿将 API Key 分享给他人或写到代码中。**

### 1.6 验证环境

```bash
python -c "import webrtcvad, pyaudio, numpy, cv2, dashscope, pydantic; print('OK')"
```

输出 `OK` 即表示环境搭建成功，可以开始开发。

## 二、日常开发流程

### 2.1 分支模型

```
main           ← 稳定版本，所有 feature 分支通过 PR 合并到此处
feature/xxx    ← 各自的功能分支，从 main 拉出
```

### 2.2 每次开发前的准备

```bash
# 1. 切回 main 分支
git checkout main

# 2. 拉取最新代码（同步协作方的变更）
git pull origin main

# 3. 从最新 main 拉出自己的功能分支
git checkout -b feature/你的功能名
```

> 功能分支命名示例：`feature/config-system`、`feature/audio-pipeline`、`feature/focus-state-machine`

### 2.3 开发中

在功能分支上正常编写代码。如果当天无法完成，记得在下班前 `git push origin feature/xxx` 推送到远程，避免本地代码丢失。

### 2.4 提交代码

```bash
# 查看变更
git status

# 暂存相关文件
git add <文件1> <文件2> ...

# 提交（使用约定前缀）
git commit -m "feat: 实现了xxx功能"

# 推送到 GitHub
git push origin feature/你的功能名
```

### 2.5 提交信息前缀约定

| 前缀 | 用途 | 示例 |
|------|------|------|
| `feat:` | 新功能 | `feat: 实现配置管理模块` |
| `fix:` | 修复 Bug | `fix: 修复 ASR 超时未重试的问题` |
| `docs:` | 文档变更 | `docs: 更新协作者方法文档` |
| `test:` | 测试相关 | `test: 添加状态机单元测试` |
| `mock:` | Mock 相关 | `mock: 新增摄像头 Mock 类` |
| `refactor:` | 重构 | `refactor: 提取消息总线为独立模块` |

### 2.6 提交 Pull Request（PR）

1. 在 GitHub 上进入仓库页面
2. 从你的 `feature/xxx` 分支向 `main` 分支创建 Pull Request
3. 填写 PR 标题和描述，说明改了什么、为什么要这样改
4. 通知协作者 Review
5. Review 通过后，由 PR 发起者在 **GitHub 仓库网页**上点击 **「Merge pull request」** 按钮合并。合并时可选勾选 **「Delete branch」** 自动删除远程功能分支

### 2.7 PR 合并后

**1. 删除远程功能分支（在 GitHub 网页上）**

若合并时未勾选「Delete branch」，请进入仓库的 **Branches** 页面（或合并完成提示页），点击已合并分支旁的 **删除图标** 即可删除远程分支。

**2. 同步本机代码**

```bash
# 切回 main 并拉取合并后的最新代码
git checkout main
git pull origin main

# 删除本地已完成的功能分支（可选）
git branch -d feature/你的功能名
```

### 2.8 电脑端测试与验证范围

项目已经在真实树莓派及完整硬件系统上验证，能够实现预期的全部功能，M10 完成结论保持不变。当前没有树莓派时，工作范围限定为电脑端测试、Windows 测试脚本与受影响文档；保留正式运行代码、硬件参数、树莓派部署设置和依赖版本。

```bash
# 默认离线测试，无需 .env、真实 Key、麦克风或树莓派
python -m pytest tests/ -v

# 仅在明确需要时调用真实云 API（可能产生费用）
python -m pytest tests/ --run-api -m api -v

# 仅在有麦克风和扬声器时执行真实音频测试
python -m pytest tests/test_real_audio.py --run-hardware -v
```

Windows 可运行 `scripts\run_headless_tests.bat`（可加 `-v`），只有加 `--api` 才启用云 API。脚本会保留 pytest 的失败退出码。新增标记需要在 `pytest.ini` 注册，测试不能用返回 `False` 或 `1` 代替失败断言。

`tests/conftest.py` 在收集阶段避免加载用户配置和 `.env`；每个测试复制独立配置，把配置、记忆、音频输出放进临时目录，并在结束时停止、等待测试创建的模拟线程。默认阻止网络和真实设备导入。不要为了测试改写本地配置，也不要让测试结束时的清理替代对被测停止方法的断言。Mock 舵机的模拟等待被测试夹具移除，仅用于缩短电脑测试，不代表真实运动速度。

离线主循环测试使用固定 LLM/ASR 响应，检查工具结果分发、会话保存与退出；它不验证云模型实际决策、树莓派多进程或真实声卡／摄像头。测试依赖使用现有环境，不以电脑安装版本重新生成树莓派依赖。

**结果报告必须区分：** `passed` 为通过断言；`skipped` 为未启用的外部测试（或非 Windows 系统不适用的批处理测试）；`xfailed` 为已执行并复现的待处理问题。下列用例使用 `xfail(strict=True, raises=AssertionError)` 保留预期行为，不能算作通过；若意外通过，测试反而失败，要求重新核查标记。使用 `--runxfail` 可将这些用例直接显示为普通失败。

| 标识 | 离线观察到的边界情况 | 本轮处理 |
|------|----------------------|----------|
| `FOCUS-PAUSED` | `complete_focus()` 拒绝从 PAUSED 状态结束，原断言要求能够结束 | 保留断言；涉及状态机和设备联动，等待树莓派验证后再改正式代码 |
| `BUS-SEND` | `send()` 把 Queue 工厂当作类型，消息没有送达；broadcast/shutdown 也使用此路径 | 保留收发结果断言；当前传感器直接 `to_main.put()` 的路径另有正常用例，不改通信架构 |
| `MOCK-CAMERA` | CameraMock 的 stop_tracking/close 没有停止后台循环 | 保留停止断言；仅在测试清理阶段显式停止并等待模拟线程，`src` 中的类不变 |

新增失败必须调查，不能照搬这些标记隐藏问题。修正旧接口测试时，以当前接口为准，同时保留有意义的行为断言。上述离线边界记录与已完成的整机验证分别报告，不据此将项目改写成“硬件尚未验证”。

本轮未修改 `scripts/run_headless_tests.sh`；旧脚本的 `--api` 没有传递新的 `--run-api` 开关。使用上面的显式 pytest 命令选择新测试集，不将旧脚本结果解释为已执行云 API 测试。

## 三、环境同步

### 3.1 当有人修改了依赖

如果项目的 `environment.yml` 或 `requirements.txt` 发生了变更（比如新增了第三方包），拉取最新代码后需要同步本地环境：

```bash
# 同步 conda 环境变更
conda env update -f environment.yml --prune

# 同步 pip 依赖变更
pip install -r requirements.txt
```

### 3.2 如果你新增了依赖

在提交代码前，务必同步更新以下文件：

| 文件 | 更新内容 |
|------|---------|
| `environment.yml` | `pip:` 段中添加新包及版本号 |
| `requirements.txt` | 添加新包及最低版本要求 |

> 原则：让协作者 `pull` 代码后只需执行 3.1 节的两条命令即可保持环境一致。

## 四、常见问题

### Q1: `conda: command not found`

Anaconda 未安装或未添加到系统 PATH。重新安装 Anaconda3 时勾选「Add Anaconda to my PATH environment variable」。

### Q2: `conda env create` 很慢

conda 默认源在海外，可配置国内镜像加速：

```bash
conda config --add channels https://mirrors.tuna.tsinghua.edu.cn/anaconda/pkgs/main/
conda config --add channels https://mirrors.tuna.tsinghua.edu.cn/anaconda/cloud/conda-forge/
conda config --set show_channel_urls yes
```

### Q3: `import webrtcvad` 报 `ModuleNotFoundError: No module named 'pkg_resources'`

webrtcvad 与新版本 setuptools 不兼容。手动降级 setuptools：

```bash
pip install "setuptools>=65.0,<70.0"
```

### Q4: 我的 `.env` 文件没生效

确认文件名是 `.env`（不是 `.env.example` 或 `.env.txt`），且文件位于项目根目录。

### Q5: 冲突了怎么办？

```bash
# 在 main 分支上拉取最新代码
git checkout main
git pull origin main

# 切回你的 feature 分支，将 main 合并进来
git checkout feature/xxx
git merge main

# 手动解决冲突文件中的 <<<<<< 标记
# 解决后：
git add <冲突文件>
git commit -m "merge: 合并 main 解决冲突"
git push origin feature/xxx
```
